# Whose move

Lens edition of `five-ways`. `five-ways` is the full version.

This skill expands `five-ways` step 0. The queue check below comes from `queue-constraint`. Run this skill before `intercept` names a way. If you make an excellent attack on a problem that is not yours, the session uses all of its effort on that problem.

## Use

- The next step needs a human action, a licence, or a secret that you do not have.
- Another session holds the file or the branch.
- A queue looks idle and cheap, and you want to add another scanner.
- Agents selected the top item again for days because its done-condition is empty.

## The move

Name exactly one of these:

- **Yours.** Code, data, or a measurement that you can take. Continue to `intercept` step 1.
- **Not yours.** An operator decision, a licence, the uncommitted tree of another person, a missing credential, or busy hardware. Write `blocked_by: <what>` and stop. Do not invent related work to avoid that sentence.
- **Not yours yet.** Say what clears the obstacle, so that the reason for the wait is clear.

If the obstacle is a queue, measure three numbers before you propose anything:

| Stage | Question |
|---|---|
| Discovery | Does the system find candidates, and from how many sources? |
| Promotion | How many items are ready and correctly formed for execution? |
| Execution | What concurrency and spend did the system actually use, and what finished? |

Usually, the jam is in promotion. More discovery makes that jam worse. If a ready item has an empty done-condition, the item is not ready.

## Recorded case

An autonomous loop once spent about one dollar of a large daily ceiling, and it looked cautious. Two items had the status "ready", and both failed lint. A large inbox of items that nobody promoted was next to them. The constraint was promotion. A timid executor was not the cause.

A false premise is still yours to name. If the task describes a component that no code calls, the correction replaces the work. That result is not a failed work item.
